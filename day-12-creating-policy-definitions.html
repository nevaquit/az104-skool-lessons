The concept

A policy definition is the rule itself, written in JSON. It has 2 halves that matter:

  • The condition (if): what the rule looks at. This is a logical test against resource properties, such as "the location field is not in the allowed list" or "the tags do not contain CostCenter."
  • The effect (then): what happens when the condition is true. Deny, Audit, DeployIfNotExists, Modify, and the rest from Day 11.

A simplified definition reads like this: if the resource location is not in the allowed locations parameter, then deny.

3 more building blocks:

  • Parameters make 1 definition reusable. Instead of hardcoding the allowed regions, the definition declares a parameter called listOfAllowedLocations, and each assignment supplies its own values. Same rule, different regions per subscription.
  • Mode controls what the rule evaluates. Mode "all" evaluates everything, including the resource group itself. Mode "indexed" skips resource groups and only evaluates the resources inside, which is faster and cheaper. Most built-in definitions use indexed.
  • Aliases are friendly names for resource properties, such as the list of VM SKUs. You will see them inside built-in definitions.

Built-in versus custom: Azure ships hundreds of built-in definitions covering common requirements (allowed locations, required tags, allowed SKUs, encryption). Create a custom definition only when no built-in fits. In the portal you build 1 under Policy, Authoring, Definitions, using the "+ Policy definition" button, or you write the JSON and import it.

Critical point: creating a definition does nothing by itself. The rule only takes effect once it is assigned to a scope (Day 13).

Key vocabulary

  • policyRule: the if/then logic inside a definition.
  • if / then: the condition block and the effect block of a policy rule.
  • field: a resource property the rule tests, such as location, type, or tags.
  • parameters: inputs that make a definition reusable; values are supplied at assignment time.
  • mode: "all" evaluates resource groups too; "indexed" evaluates only resources.
  • aliases: shorthand names for resource properties used in rules.

Try it

You need any Azure account, including a free 1. This lab is read only. Nothing is created or changed.

In the portal:

  1. Open Policy, then under Authoring open Definitions.
  2. Search for "Require a tag on resource groups" and open it.
  3. Select View definition to see the JSON. Find the "policyRule" section and the "then" block that holds the effect.
  4. Find the "parameters" section. Notice the tag name is a parameter, not hardcoded. That value gets filled in when the definition is assigned.

In the CLI (Cloud Shell is fine):

  1. Show 1 built-in definition's name and mode: az policy definition list --query "[?displayName=='Require a tag on resource groups'].{Name:name, Mode:mode}" --output table

Clean up: nothing was created or changed.

Worked example: Meridian Health

Meridian's finance team requires a CostCenter tag on every resource group for chargeback. The built-in "Require a tag on resource groups" is close but the team wants the tag name pre-filled and a custom description for auditors. The cloud admin clones the built-in into a custom definition, sets the default tag name parameter to CostCenter, and saves it. The definition sits idle until tomorrow, when it gets assigned (Day 13). Definition first, assignment second, always in that order.

Exam tip

The exam tests the difference between a definition and an assignment far more than JSON authoring. If a question asks where the rule is written, that is the definition. If it asks where the rule applies, that is the assignment. You will not be asked to write policy JSON from memory.

Key takeaways

  • A definition is JSON with an if (condition) and a then (effect).
  • Parameters make definitions reusable; assignments supply the values.
  • Mode "indexed" skips resource groups and is the common choice; mode "all" evaluates everything.
  • Prefer built-in definitions; go custom only when nothing fits.
  • A definition enforces nothing until it is assigned to a scope.
