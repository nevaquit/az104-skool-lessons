The concept

Assigned groups (Day 26) break the moment HR forgets to tell IT about a transfer. Dynamic groups fix that: membership follows a rule written against user or device attributes, and Entra ID adds and removes members automatically as attributes change.

A rule has 3 parts: a property, an operator, and a value. Examples:

  • user.department -eq "Sales": every user whose department is Sales.
  • user.jobTitle -contains "Nurse": every user with Nurse in the title.
  • user.accountEnabled -eq true: every enabled user account.
  • device.deviceOSType -eq "Windows": for dynamic device groups.

The rule builder in the portal helps you assemble these without memorizing syntax, and Validate rules previews exactly which users match before you commit. Always validate: a typo in the property name silently matches nobody, and you find out during an outage.

The rules that matter for the exam:

  1. License. Every user who benefits from dynamic group membership needs a Microsoft Entra ID P1 or P2 license. No P1, no dynamic groups. This is the single most tested fact in this lesson.
  2. 1 membership type per group. A group is either assigned or dynamic, never mixed. Convert by changing the membership type, which clears existing members.
  3. No nesting, no guests in some rules. Dynamic groups cannot contain other groups, and guest users are excluded from certain rule evaluations. Keep rules to member users and devices.
  4. Attributes must be populated. The rule only works if the attribute is actually filled in. user.department -eq "Sales" matches nobody if HR never sets the department field. Garbage in, empty group out.

Dynamic groups shine for licensing and access that follows the org chart: "all nurses get the clinical app," "all Windows devices get the baseline policy." The membership stays correct because the attributes stay correct.

Key vocabulary

  • Dynamic membership rule: a property, operator, and value expression that selects members automatically.
  • Rule builder: the portal designer for building and validating membership rules.
  • Validate rules: previews which users or devices match a rule before the group is created.
  • Dynamic device group: a dynamic group whose members are devices, using properties like deviceOSType.

Try it

Free and safe: you build and validate a rule but do not create the group, because creating a dynamic group requires P1.

In the portal:

  1. In the Microsoft Entra admin center, open Identity > Groups > All groups > New group.
  2. Set group type to Security and membership type to Dynamic user. Click Dynamic query to open the rule builder.
  3. Build a rule: property department, operator Equals, value Sales. (Any attribute works; the point is the workflow.)
  4. Click Validate rules and review the preview list of matching users. Note users with a blank department do not match.
  5. Click Cancel all the way out. Do not create the group.

Clean up: nothing was created. The exercise was the builder and the validation preview.

Worked example: Meridian Health

Meridian Health's "All-Nurses" group used to be maintained by hand, and every month 2 or 3 nurses were missing access to the clinical app on their first day. The admin replaces it with a dynamic group ruled user.jobTitle -contains "Nurse". Now HR sets the job title during onboarding and the nurse lands in the group, gets the app, and gets the license automatically. When a nurse transfers to administration and the title changes, the membership drops off by itself. The helpdesk's monthly "fix the nurse group" ticket disappears.

Exam tip

"P1 or P2 required for dynamic groups" is the headline fact; the exam pairs it with scenarios that say "minimize cost" to rule the feature out. Second headline: validate rules before saving, because attribute typos fail silently.

Key takeaways

  • Dynamic groups select members automatically from attribute rules: property, operator, value.
  • Every user benefiting from dynamic membership needs a P1 or P2 license.
  • Always use Validate rules to preview matches before creating the group.
  • A group is either assigned or dynamic, never both; no nesting.
  • Rules only work when the attributes they test are actually populated.
