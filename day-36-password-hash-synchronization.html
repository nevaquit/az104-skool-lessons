The concept

Password hash synchronization is the simplest of the 3 Entra Connect sign-in methods, and it is the Express setup default. The idea: users keep signing in with the same on-premises password, but authentication happens against Entra ID in the cloud.

What actually syncs is not the password. The on-premises password hash is hashed a second time (with a per-user salt) before it ever leaves the building, and only that second hash is stored in Entra ID. Microsoft cannot reverse it back into the password. When the user signs in to a cloud app, Entra ID hashes what they typed the same way and compares hashes.

Why organizations choose it:

  • Resilience: sign-in keeps working even if the on-premises network or domain controllers go down, because the cloud has everything it needs.
  • Simplicity: no extra agents, no federation servers. It is the default for a reason.
  • Security extras unlocked: because the hashes live in Entra ID, Microsoft can run the leaked credentials report (it checks sign-in hashes against known breach dumps) and Identity Protection gets full signal (Day 38).
  • Plays well with others: works with Seamless SSO for silent sign-on inside the network, and with password writeback so cloud password changes flow back on-premises.

The honest limitation: the password policy enforced at cloud sign-in is Entra ID's cloud policy, not your on-premises fine-grained password policy. If the business requires on-premises policy enforcement at every cloud sign-in, that is pass-through authentication (Day 37).

Key vocabulary

  • Password hash synchronization (PHS): syncs a salted hash of the on-premises password hash to Entra ID; the cloud authenticates.
  • Hash of a hash: the on-premises hash is hashed again with a per-user salt before syncing; the plaintext password never travels.
  • Leaked credentials report: flags users whose credentials appear in public breach dumps; only possible because hashes are in the cloud.
  • Seamless SSO: silent sign-in from domain-joined devices; pairs with PHS.

Worked example: Meridian Health

Meridian Health chose PHS during their Entra Connect Custom setup. 6 months later a fiber cut took a rural clinic offline from the hospital data center for a day. Staff at that clinic still signed in to Microsoft 365 and Teams because authentication happened in Entra ID, not against the unreachable domain controllers. The following quarter, the leaked credentials report flagged 11 staff members reusing passwords found in breach dumps, and the helpdesk walked each 1 through a reset.

Exam tip

The exam contrasts PHS against pass-through authentication directly. Anchor it this way: PHS means the cloud validates (resilient, simple, default). If the scenario says "sign-in must keep working during an on-premises outage," the answer is PHS. If it says "passwords must be validated against on-premises Active Directory," that is tomorrow's lesson.

Key takeaways

  • PHS syncs a salted hash of the on-premises hash, never the password itself.
  • Authentication happens in Entra ID, so sign-in survives on-premises outages.
  • It is the Express default and the simplest of the 3 sign-in methods.
  • It unlocks the leaked credentials report and full Identity Protection signal.
  • The cloud password policy applies at sign-in, not your on-premises fine-grained policy.
