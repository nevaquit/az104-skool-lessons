The concept

If users are the "who" (Day 23), groups are how you manage the "who" at scale. You never assign access to 200 individuals when you can assign it once to the group they belong to. 2 group types, 2 membership styles:

Group types:

  • Security groups: for access control. Assign Azure RBAC roles to them, gate apps behind them, use them in Conditional Access. This is the AZ-104 workhorse.
  • Microsoft 365 groups: for collaboration. They come with a Teams team, a SharePoint site, and a shared mailbox. Use them when people work together, not when you are gating access.

Membership styles:

  • Assigned: you add and remove members by hand. Simple, predictable.
  • Dynamic: membership follows a rule, like "all users in the Sales department" (Day 27). Needs P1 or P2.

Owners vs members. Every group has owners who can manage membership. Members just get whatever the group grants. On the exam, "who can add users to this group" is always answered by ownership, not by admin roles.

The nesting rule. Entra ID does not support nested security groups: you cannot put a group inside another security group. If the scenario needs layered access, flatten it: put the users in each group directly. This trips up admins coming from on-premises AD, where nesting is normal.

Roles on groups. You can assign Microsoft Entra directory roles (like User Administrator) to groups, but that requires P1 or P2. Same for group-based licensing: assign a license to the group once and every member inherits it, instead of licensing users 1 by 1.

Key vocabulary

  • Security group: a group used for access control: RBAC assignments, app access, Conditional Access targeting.
  • Microsoft 365 group: a collaboration group with Teams, SharePoint, and a shared mailbox.
  • Assigned membership: members added and removed manually.
  • Dynamic membership: members selected automatically by an attribute rule (P1 or P2 required).
  • Group owner: the person who can manage a group's membership.

Try it

Free. You create a security group, manage its membership, and delete it.

In the portal:

  1. In the Microsoft Entra admin center, open Identity > Groups > All groups > New group.
  2. Set group type to Security, name it Lab-Storage-Readers, and membership type to Assigned. Create it.
  3. Open the group, go to Members > Add members, and add your Day 23 style test user (or any lab user). Confirm the member appears.
  4. Open Owners > Add owners and note you can delegate membership management without making anyone an admin.
  5. Remove the member, then delete the group (Delete on the group page).

In the CLI (Cloud Shell is fine):

  1. Create the group: az ad group create --display-name "Lab-Storage-Readers" --mail-nickname "labstoragereaders".
  2. Add a member (use the member's object ID or UPN): az ad group member add --group "Lab-Storage-Readers" --member-id "<user-object-id-or-upn>".
  3. Verify: az ad group member list --group "Lab-Storage-Readers" --output table.
  4. Delete the group: az ad group delete --group "Lab-Storage-Readers".

Clean up: member removed, group deleted. Nothing billable was created.

Worked example: Meridian Health

Meridian Health stops assigning the Reader role to individual billing clerks. Instead, the admin creates a security group called Billing-Readers, adds the 8 clerks, and assigns Reader on the billing subscription to the group once (the Day 19 move). When a 9th clerk joins, the helpdesk adds her to the group and she instantly has exactly the right access. When someone transfers out, removing them from the group revokes everything. Auditors love this: 1 group, 1 role assignment, 1 place to review.

Check your understanding

  1. You need to gate an application to 300 users and review the access quarterly. Security group or 365 group, and why?
  2. Can you add the "Nurses" security group as a member of the "Clinical-Staff" security group?
  3. Who can add members to a group: any member, or only specific people?
  4. Your company has no P1 licenses. Can you assign the User Administrator directory role to a group?

Exam tip

2 facts do most of the work on group questions: no nested security groups in Entra ID, and role-assignable groups plus group-based licensing need P1 or P2. If a scenario says "no premium licenses," dynamic membership and role assignment to groups are off the table.

Key takeaways

  • Security groups gate access; Microsoft 365 groups enable collaboration.
  • Assigned membership is manual; dynamic membership follows attribute rules and needs P1 or P2.
  • Group owners manage membership; members just receive access.
  • Entra ID does not support nested security groups.
  • Assigning directory roles to groups and group-based licensing require P1 or P2.
