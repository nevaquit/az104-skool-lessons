The concept

Built-in roles cover common jobs, but sometimes no built-in matches least privilege. The helpdesk needs to restart virtual machines but must not delete them, change networks, or touch storage. No built-in does exactly that. That gap is what custom roles fill.

A custom role is a JSON document with 5 permission fields:

  • Actions: the allowed control plane operations. Wildcards work: "Microsoft.Compute/virtualMachines/*" allows everything on VMs, while listing "Microsoft.Compute/virtualMachines/read", "Microsoft.Compute/virtualMachines/start/action", and "Microsoft.Compute/virtualMachines/restart/action" allows only viewing, starting, and restarting.
  • NotActions: subtractions from Actions, used to carve out dangerous operations.
  • DataActions and NotDataActions: the same idea for the data plane.
  • AssignableScopes: where this role may be assigned, such as a subscription or management group. A custom role can only be assigned inside its assignable scopes, so this field is also a guardrail.

Plus the identity fields: Name, Description, and a flag marking it custom.

2 ways to create 1. In the portal: open Access control (IAM), select Add, then Add custom role. You can clone an existing role and edit it, which is faster and safer than starting from blank JSON, or paste your own JSON. In the CLI: save the JSON to a file and run az role definition create --role-definition <file.json>.

After creating it, verify with Check access before rolling it out: assign it to a test group, confirm the effective permissions look right, and only then assign it for real.

Key vocabulary

  • Actions / NotActions: allowed control plane operations, minus carved-out exceptions.
  • DataActions / NotDataActions: allowed data plane operations, minus exceptions.
  • AssignableScopes: the scopes where the custom role may be assigned.
  • Clone a role: starting a custom role from a built-in role's permission set.

Try it

You need any Azure account, including a free 1. You will walk the custom role wizard and cancel before creating anything.

In the portal:

  1. Open a subscription or resource group, then Access control (IAM), then Add, then Add custom role.
  2. Choose Clone a role and pick Reader as the baseline.
  3. In the JSON editor, add to Actions: "Microsoft.Compute/virtualMachines/start/action" and "Microsoft.Compute/virtualMachines/restart/action".
  4. Step through the tabs to Review + create, read the summary, then Cancel instead of creating. Nothing is saved.

The CLI alternative (described, not executed):

  1. Save your role JSON to a file, for example vm-operator.json, with Name, Actions, NotActions, and AssignableScopes filled in.
  2. Create it with: az role definition create --role-definition vm-operator.json

Clean up: the wizard was cancelled, so no custom role was created.

Worked example: Meridian Health

Meridian's helpdesk handles VM reboots for the whole company. Giving them Virtual Machine Contributor would also let them delete VMs and resize them, which is more power than the job needs. The cloud team creates a "VM Operator" custom role:

  • Actions: read virtual machines, start, restart, and deallocate them.
  • NotActions: delete virtual machines.
  • AssignableScopes: the Meridian-Prod subscription.

Assigned to the helpdesk Entra group, the role lets technicians fix stuck VMs at 3 AM without the ability to destroy anything. When auditors ask why helpdesk staff cannot delete production VMs, the NotActions entry is the documented answer.

Exam tip

The exam tests the building blocks, not JSON memorization: Actions versus DataActions, what NotActions does, and that AssignableScopes limits where the role can be used. If a scenario says "no built-in role fits" or "must not be able to delete," think custom role.

Key takeaways

  • Create custom roles when no built-in role matches least privilege.
  • Actions and DataActions grant; NotActions and NotDataActions carve back.
  • Wildcards like "Microsoft.Compute/virtualMachines/*" are powerful, so prefer narrow action lists.
  • AssignableScopes limits where the role may be assigned.
  • Clone a built-in role instead of starting from blank JSON, and verify with Check access.
