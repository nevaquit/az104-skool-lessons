The concept

Conditional Access is the Zero Trust policy engine in Microsoft Entra ID. The old model trusted anyone inside the office network. The new model evaluates every sign-in and asks: should this user, on this device, from this location, get access to this app right now?

Every policy is an if-then statement with 2 halves:

Assignments (the IF): who and what the policy applies to.

  • Users: specific users or groups, or all users. You can include and exclude. Directory roles (like Global Administrator) can be targeted directly.
  • Target resources: which cloud apps, or user actions such as registering devices.
  • Conditions: network (location, built from named locations such as trusted office IP ranges), device platform (Windows, iOS, Android), client apps (browser vs mobile app), and sign-in risk (requires P2).

Access controls (the THEN): what happens when the IF matches.

  • Grant controls: block access, or allow access but require something first: require multifactor authentication, require a compliant device, require a hybrid joined device, require an approved client app. You can combine them and choose whether the user must satisfy 1 or all of them.
  • Session controls: limit what happens after sign-in, such as sign-in frequency (force reauthentication every X hours) or a persistent browser session.

How policies combine: if 3 policies apply to a sign-in, the user must satisfy all 3. And a Block in any 1 policy wins over Grants in the others.

2 non-negotiable safety practices:

  1. Test before enforcing. Use the What If tool to preview which policies hit a given sign-in, and roll new policies out in Report-only mode first so you can read the impact in the sign-in logs without blocking anyone.
  2. Keep a break-glass account. Exclude at least 1 emergency access admin account from every policy. 1 bad policy can otherwise lock every administrator out of the tenant.

Licensing fact the exam loves: Conditional Access requires Microsoft Entra ID P1 or P2. It is included in EMS E3/E5 and Microsoft 365 E3/E5 plans.

Key vocabulary

  • Conditional Access policy: an if-then rule evaluated at every sign-in.
  • Assignments: the who, what, and conditions a policy applies to.
  • Grant controls: block or allow-with-requirements (MFA, compliant device, hybrid joined device).
  • Session controls: limits applied after sign-in (sign-in frequency, persistent browser).
  • Named location: a defined set of IP ranges or countries, such as trusted office networks.
  • Report-only mode: a policy state that logs what would happen without enforcing it.
  • What If: a tool that previews which policies apply to a simulated sign-in.
  • Break-glass account: an emergency admin account excluded from Conditional Access.

Try it

Conditional Access needs a P1 or P2 license to enforce. Everything below is safe on a free tenant; enforce nothing unless you have a trial license.

In the portal:

  1. Open the Microsoft Entra admin center (entra.microsoft.com) and go to Protection > Conditional Access > Policies. Note the State column: On, Off, or Report-only.
  2. Select + Create new policy (do not save it yet) and study the 2 halves: Assignments (Users, Target resources, Conditions) and Access controls (Grant, Session). Cancel out of the wizard when done.
  3. Go to Conditional Access > Named locations and see how trusted IP ranges are defined.
  4. If your tenant has a P1 trial: create a real policy named "CA-Lab-ReportOnly" targeting your own account, all cloud apps, Grant = Require multifactor authentication, and set Enable policy to Report-only. Create it, then check Monitoring > Insights and reporting later to see it evaluate your sign-ins.

CLI alternative (read-only):

List policies through Microsoft Graph:

az rest --method get --url "https://graph.microsoft.com/v1.0/identity/conditionalAccess/policies" --query "value[].{Name:displayName, State:state}" --output table

Clean up: delete the "CA-Lab-ReportOnly" policy if you created 1.

Worked example: Meridian Health

Meridian Health builds 3 policies:

  • CA-Admins-Require-MFA: Users = directory role Global Administrator, Target = all cloud apps, Grant = require multifactor authentication.
  • CA-Block-Legacy-Auth: Conditions = client apps set to legacy authentication clients, Grant = block access.
  • CA-PatientApp-Compliant-Device: Target = the patient records app, Grant = require compliant device.

The account emergency-admin@meridianhealth.org is excluded from all 3. New policies spend a week in Report-only while the team reads the sign-in logs, then get switched on.

Check your understanding

  1. 1 policy grants access when MFA is completed. Another policy blocks access from untrusted locations. A user completes MFA from an untrusted location. What happens?
  2. Which license is required to enforce Conditional Access policies?
  3. Why should every tenant exclude a break-glass account from its Conditional Access policies?
  4. What are the 2 modes you should use to test a policy before enforcing it?

Exam tip

Conditional Access questions test the if-then structure: match the scenario to assignments and grant controls. "Require MFA for administrators" means Users = directory roles, Target = all cloud apps, Grant = require MFA. 2 facts carry the most points: P1 or higher is required, and Block beats Grant when policies combine.

Key takeaways

  • Conditional Access is the Zero Trust engine evaluated at every sign-in.
  • Policies have 2 halves: assignments (who, what, conditions) and access controls (grant, session).
  • When several policies apply, the user must satisfy all of them; a Block in any policy wins.
  • Enforcement requires Microsoft Entra ID P1 or higher.
  • Always test with What If and Report-only mode, and always keep a break-glass account excluded.
