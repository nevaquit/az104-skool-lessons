The concept

Security Defaults are Microsoft's free, all-or-nothing security baseline for every Entra ID tenant. No P1, no P2, no configuration expertise required: flip 1 switch and every user gets a bundle of protections. New tenants created after late 2019 have it on by default.

What the switch turns on:

  • MFA registration for everyone. All users have 14 days to register MFA methods. Miss the deadline and sign-in is blocked until they register. No exceptions, no exclusions.
  • MFA for administrators, always. Anyone with an admin role (Global Administrator, User Administrator, and the rest) must do MFA on every sign-in.
  • MFA for risky sign-ins and privileged actions. Accessing the Azure portal and other privileged actions requires the extra proof.
  • Legacy authentication blocked. Old protocols that cannot do MFA (like basic authentication to Exchange) are shut off at the tenant level. This alone kills entire classes of password-spray attacks.

The 2 limits that define every exam question about Security Defaults:

  1. All or nothing. You cannot scope it to a pilot group, exclude the CEO, or customize which protections apply. It is the whole bundle for everyone or it is off.
  2. Mutually exclusive with Conditional Access. The moment you create your first Conditional Access policy, Security Defaults must be turned off. They cannot run together. The exam frames this as a migration path: start on Security Defaults for free, move to Conditional Access when you buy P1.

So the decision tree is simple: no premium licenses and need org-wide MFA? Security Defaults. Need exceptions, granular control, or named locations? Buy P1 and move to Conditional Access (Day 31).

Key vocabulary

  • Security Defaults: the free, tenant-wide baseline enforcing MFA registration, admin MFA, and legacy auth blocking.
  • Legacy authentication: older protocols (like basic auth) that cannot handle MFA. Blocked under Security Defaults.
  • 14 day registration window: new users must register MFA methods within 14 days or sign-in is blocked.
  • Conditional Access: the P1 or P2 policy engine that replaces Security Defaults when you need customization.

Try it

Read-only by design. Toggling this setting changes security for the whole tenant, so this lab is locate-and-read only.

In the portal:

  1. In the Microsoft Entra admin center, open Identity > Overview > Properties.
  2. At the bottom, find Security defaults and click Manage security defaults. Read the current setting (Enabled or Disabled) and the explanatory text.
  3. Note what the page says about Conditional Access: enabling any Conditional Access policy requires Security Defaults to be off.
  4. Close the blade without changing anything.

In the CLI:

  1. There is no supported CLI toggle for this tenant-level switch that you should script casually; the portal blade in step 2 is the documented path. Treat the setting as portal-managed.

Clean up: nothing was changed. If the setting was Enabled when you arrived, it is still Enabled.

Worked example: Meridian Health

Meridian Health's new dev-test tenant starts life with Security Defaults on: every developer registers the Authenticator app within 14 days, legacy auth is blocked, and the 2 subscription admins do MFA every sign-in. 6 months later Meridian buys P1 licenses because the helpdesk wants to exclude the break-glass emergency accounts from MFA and skip MFA on the office network. The admin creates the first Conditional Access policy, which forces Security Defaults off, and rebuilds each baseline protection as a granular policy. Same protections, now customizable.

Check your understanding

  1. A startup has no premium licenses and needs MFA for all 30 users this week. What do you enable?
  2. Can you enable Security Defaults for only the IT department?
  3. You create your first Conditional Access policy. What must happen to Security Defaults, and why?
  4. A service account uses a legacy protocol that cannot do MFA. What breaks when Security Defaults turn on?

Exam tip

Security Defaults questions always hinge on the 2 limits: free and all-or-nothing, and incompatible with Conditional Access. If the scenario mentions any exception, exclusion, or customization, Security Defaults is the wrong answer and Conditional Access is the right 1.

Key takeaways

  • Security Defaults are the free baseline: MFA registration within 14 days for all users, always-on MFA for admins, legacy authentication blocked.
  • All or nothing: no scoping, no exclusions, no customization.
  • New tenants get it on by default; it cannot run alongside Conditional Access.
  • The upgrade path is P1 plus Conditional Access when you need granularity.
  • Legacy protocols that cannot do MFA stop working when Security Defaults are on.
