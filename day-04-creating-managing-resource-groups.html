The concept

A resource group is a logical container for resources. Every resource in Azure lives in exactly 1 resource group: no more, no less. Resource groups are how you organize the lifecycle of things that live and die together.

5 facts that carry the exam weight:

  1. 1 resource group per resource. A VM cannot sit in 2 resource groups at once.
  2. The resource group has a location, and it is only metadata. The location you pick stores the resource group's metadata. Resources inside the group can live in completely different regions. An East US resource group can hold a storage account in West Europe.
  3. You cannot nest resource groups and you cannot rename 1. To "rename," you create a new resource group and move the resources (Day 5).
  4. Deleting a resource group deletes everything inside it. This is the fastest cleanup tool in Azure and the most dangerous click in the portal. The exam loves "accidental deletion" scenarios.
  5. Resource groups are a scope. RBAC roles, policies, tags, and locks can all be assigned at the resource group level, affecting everything inside.

Good naming conventions pay off at 2 in the morning: rg-patientportal-prod tells you the container type, the app, and the environment in 1 glance.

Key vocabulary

  • Resource group: a logical container for Azure resources. Every resource belongs to exactly 1.
  • Location (region): for a resource group, the region where its metadata is stored. It does not restrict where member resources live.
  • Resource: anything you create in Azure: VMs, storage accounts, virtual networks, and more.
  • Deployment: the act of creating resources, often from a template, into a resource group.

Try it

Creating and deleting an empty resource group is free.

In the portal:

  1. Search for Resource groups and open it. Click Create.
  2. Pick your subscription, enter the name rg-az104-day04, and choose a region, for example East US. Note the region picker: this sets the metadata location only.
  3. Click Review + create, then Create. Open the new group and confirm it is empty.

In the CLI (Cloud Shell is fine):

  1. Create 1: az group create --name rg-az104-day04-cli --location eastus.
  2. List your groups: az group list --query "[].{name:name, location:location}" --output table.
  3. Clean up both groups: az group delete --name rg-az104-day04 --yes and az group delete --name rg-az104-day04-cli --yes.

Clean up: both lab resource groups deleted. Verify with az group list --output table.

Worked example: Meridian Health

Meridian Health standardizes on rg-<app>-<env> names in East US:

  • rg-patientportal-prod: the patient portal and its database
  • rg-patientportal-dev: the dev copy
  • rg-backup-prod: Recovery Services vaults

When the dev environment is rebuilt each quarter, the team deletes rg-patientportal-dev and recreates it. 1 delete removes every dev resource at once, which is exactly why production resource groups also get a delete lock (you will meet locks on Day 293, but remember the danger now).

Check your understanding

  1. Can a single virtual machine belong to 2 resource groups at the same time?
  2. Your resource group is in East US. Can it contain a storage account in West Europe? Why?
  3. What happens to the resources when you delete their resource group?
  4. True or false: you can rename a resource group in the portal.

Exam tip

"Someone deleted the resource group" is exam shorthand for "everything inside is gone." The fix the exam wants is prevention: resource locks and careful RBAC. Also remember the location trap: the resource group location restricts nothing about where member resources live.

Key takeaways

  • Every Azure resource lives in exactly 1 resource group.
  • The resource group location stores metadata only; member resources can live anywhere.
  • Resource groups cannot be nested or renamed.
  • Deleting a resource group deletes everything inside it.
  • Resource groups are a scope for RBAC, policy, tags, and locks.
