The concept

Pass-through authentication is the second Entra Connect sign-in method, and it answers a different requirement than yesterday's lesson. With PTA, the password is validated against on-premises Active Directory at the moment of sign-in. No password hash is stored in the cloud in any form.

How it works: you install lightweight authentication agents on domain-joined servers inside your network (no inbound firewall holes needed; the agents make outbound connections only). When a user signs in to a cloud app, Entra ID hands the username and password to an agent, the agent validates them against a domain controller, and the result comes back. The whole exchange is encrypted.

Why organizations choose it:

  • No password material in the cloud. For some compliance regimes, that is the deciding factor.
  • On-premises policies enforced everywhere. Account lockout, password complexity, and expiry rules from your on-premises domain apply to cloud sign-ins too, because the domain controller is doing the validating.
  • Simple to deploy. No federation infrastructure, just agents.

What it demands in return:

  • High availability is your job. Microsoft recommends at least 3 agents spread across servers. If the agents or the domain controllers are unreachable, cloud sign-in stops. Compare that with PHS, which keeps working through an outage.
  • Plan the placement. Agents belong on dedicated, always-on, domain-joined servers, not on the domain controllers themselves.

PTA is commonly paired with Seamless SSO: inside the corporate network users get silent sign-on, and every validation still runs against on-premises AD.

The 3 methods side by side, which is exactly how the exam frames it:

  • Where validated: PHS in Entra ID (cloud); PTA in on-premises AD via agents; federation in the on-premises federation service
  • Password material in cloud: PHS stores a salted hash; PTA and federation store none
  • Survives on-premises outage: PHS yes; PTA no; federation no
  • Complexity: PHS lowest; PTA low; federation highest

Key vocabulary

  • Pass-through authentication (PTA): passwords validated against on-premises AD at sign-in; nothing stored in the cloud.
  • Authentication agent: the lightweight service that carries validation requests to domain controllers.
  • On-premises validation: the domain controller, not Entra ID, decides if the password is correct.

Worked example: Meridian Health

Meridian Health's compliance team ruled that the on-premises lockout policy must apply to every sign-in, including cloud apps used by billing staff. So the billing department's Entra Connect configuration uses PTA, with 3 agents installed across 2 hospital data centers. During a planned Active Directory maintenance window, the team posts a notice: cloud sign-in will pause for 2 hours. They accept that tradeoff because the policy requirement is non-negotiable. The clinical side, where uptime matters more, stays on PHS.

Exam tip

The exam contrasts PHS and PTA in a single question stem. Anchor: PHS means the cloud validates (resilient), PTA means on-premises validates (policy control). Trigger phrases: "agents," "password never stored in the cloud," or "on-premises lockout policy must apply" all point to PTA. "Must work during an outage" points to PHS.

Key takeaways

  • PTA validates passwords against on-premises AD at sign-in; no password material lives in the cloud.
  • On-premises password and lockout policies apply to cloud sign-ins.
  • Deploy at least 3 agents for high availability; if AD is unreachable, cloud sign-in stops.
  • Pair with Seamless SSO for silent sign-on inside the network.
  • Choose PTA for policy control, PHS for resilience, federation only when full on-premises control is required.
