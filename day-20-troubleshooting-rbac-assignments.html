The concept

"Access denied" in Azure has several possible authors: RBAC, Policy, a resource lock, or the sign-in itself. Troubleshooting means identifying which 1 said no, then fixing that layer. Work the checklist in order:

  1. Right principal? Confirm the object ID. Guests and members are different objects, and a group assignment only helps if the user is actually in the group. The classic miss: assigning to the wrong "John Smith" in a large tenant.
  2. Right scope? Assignments inherit downward, never sideways. An assignment on resource group A does nothing for resource group B. Sketch the scope chain: management group, subscription, resource group, resource.
  3. Right role? Open the role's JSON and check Actions. 2 favorites on the exam: Contributor cannot read storage blobs (that needs DataActions), and Contributor cannot assign roles (that needs Owner or User Access Administrator).
  4. Deny assignment or lock? Check access shows deny assignments, which override everything. A ReadOnly or CanNotDelete lock also overrides RBAC: an Owner blocked by a lock has an RBAC-clean setup.
  5. PIM activation? The assignment may be eligible rather than active. The user must activate it in PIM before the permissions apply.
  6. Propagation and token? New assignments take several minutes everywhere. Sign out and back in to force a fresh token; stale tokens carry stale permissions.
  7. Is it RBAC at all? Read the error. AuthorizationFailed means RBAC denied the action. A policy violation names the policy. A lock error names the lock. A sign-in failure is Entra ID or Conditional Access, not RBAC.

Most real cases end at step 3 or 6: the wrong role, or impatience.

Key vocabulary

  • Effective permissions: the union of all of a principal's assignments after inheritance.
  • Inheritance: assignments flow downward through scopes, never sideways.
  • AuthorizationFailed: the error code that means RBAC denied the action.
  • Token refresh: signing out and in to pick up changed permissions.

Try it

You need any Azure account, including a free 1. This lab is read only. Nothing is created or changed.

In the portal:

  1. Pick a resource group, open Access control (IAM), then the Check access tab.
  2. Search for your own user. Review each assignment: the role, the scope, and whether it is inherited from a parent scope.
  3. Open the Deny assignments tab and confirm whether any deny assignments apply to you.
  4. Pick 1 assignment and trace it: which scope granted it, and what would lose access if that assignment were removed.

In the CLI (Cloud Shell is fine):

  1. List everything assigned to you, everywhere: az role assignment list --assignee "<your-upn>" --all --query "[].{Role:roleDefinitionName, Scope:scope}" --output table

Clean up: nothing was changed.

Worked example: Meridian Health

3 tickets, 3 different authors:

  • Ticket 1: A developer with Contributor on Meridian-DevTest cannot open blobs in a storage account. Checklist step 3: Contributor is management plane only. Fix: add Storage Blob Data Contributor. RBAC was the author, and the role was wrong.
  • Ticket 2: A senior admin with Owner cannot delete the audit storage account. Checklist step 4: a CanNotDelete lock is on the account. Fix: nothing wrong with RBAC; the lock is doing its job and stays.
  • Ticket 3: A new hire added to the Contributors group still cannot create VMs 2 minutes later. Checklist step 6: propagation. Fix: wait several minutes, then sign out and back in for a fresh token. No configuration change needed.

Check your understanding

  1. A deployment fails with AuthorizationFailed. What does that tell you about which layer said no?
  2. A user has Owner on a resource group but cannot delete 1 storage account inside it. What do you check first?
  3. Someone was added to the Contributors group 3 minutes ago and still cannot act. Name 2 possible causes.
  4. True or false: signing out and back in can fix an access problem, and here is why.

Exam tip

Read the error text before touching anything: AuthorizationFailed is RBAC, a named policy is Policy, a named lock is a lock, and a sign-in failure is identity, not authorization. The exam writes distractors that mix these layers, so the error message is your fastest filter.

Key takeaways

  • Troubleshoot in order: principal, scope, role, deny assignment or lock, PIM activation, propagation and token.
  • Assignments inherit downward only; sideways access needs its own assignment.
  • Contributor cannot read data (no DataActions) and cannot grant access.
  • Locks and deny assignments override RBAC, including Owner.
  • New assignments need several minutes; a fresh sign-in refreshes the token.
